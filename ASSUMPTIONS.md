# Assumptions and Interpretation Decisions

The brief leaves a number of details open. This document lists every decision taken, with the reasoning,
so reviewers can see what was assumed rather than having to infer it from the code.

## Scope and environment

1. **Single currency.** All accounts share one implicit currency; amounts carry no currency code.
   Adding a `currency` column to accounts and rejecting cross-currency transfers would be the first step
   towards multi-currency support.
2. **No authentication / authorisation.** The brief does not ask for it; every endpoint is open. In a real
   deployment accounts would be scoped to an authenticated principal.
3. **Schema management via `create_all`.** Tables, constraints and triggers are created automatically on
   start-up, which keeps "runnable locally" to a single command. A production system would use Alembic
   migrations instead.
4. **SQLite is the default database** because it needs zero setup; **PostgreSQL** is fully supported
   (`DATABASE_URL`, Docker Compose) and the complete test-suite runs against both. Other SQLAlchemy-backed
   databases should work but were not tested.

## Identifiers and timestamps

5. **UUID v4 identifiers** for accounts, transactions and transfers – globally unique and not guessable.
   Internally every table also has an auto-incrementing `seq` column used purely as an insertion-order
   tie-breaker; it is not exposed.
6. **`created_at` is generated by the server in UTC** and returned as ISO-8601 with microsecond precision
   and a `Z` suffix. Clients cannot supply it.

## Money

7. **Amounts have at most two decimal places** and are `> 0`. Input may be a JSON number (`100`, `12.5`) or
   a numeric string (`"12.50"`); more than two decimals (`1.005`) is a validation error rather than being
   silently rounded, since silently rounding money is a classic source of reconciliation bugs.
8. **Amounts are stored as integer minor units** (`12.50` → `1250`) in `BIGINT` columns. This keeps all
   arithmetic and the `balance >= 0` database constraint exact on every database engine.
9. **Money is returned as a string with exactly two decimals** (`"150.00"`). JSON numbers are IEEE-754
   floats in most clients; strings avoid `150.00000000000003`-style artefacts. The brief's examples
   (`Current balance: 100`) therefore appear as `"100.00"`.
10. **Upper bound:** amounts up to 15 digits (`9,999,999,999,999.99`) are accepted – comfortably within
    `BIGINT` after conversion to minor units.

## Accounts

11. **`name` is required, trimmed, non-blank and at most 100 characters.** Names do not have to be unique
    (two people can share a name).
12. **The client cannot set `balance`, `id` or `created_at`.** Request bodies use strict validation
    (`extra = forbid`), so a request containing `balance` is rejected with `400 VALIDATION_ERROR` rather
    than silently ignored. This makes the rule explicit and visible to the client.

## Transactions

13. **Transaction `type` must be exactly `credit` or `debit` (lowercase).** `CREDIT` or `Debit` is a
    validation error, keeping the accepted vocabulary unambiguous.
14. **`description` is optional** (max 500 characters) because the brief does not list it among the
    mandatory validations; it is returned as `null` when omitted.
15. **`reference_id` is required**, trimmed, max 100 characters and **unique per account** – enforced by a
    database `UNIQUE (account_id, reference_id)` constraint in addition to an application pre-check. The
    same `reference_id` may be reused on other accounts, as the brief requires.
16. **Duplicate submissions answer `409 Conflict`** with code `DUPLICATE_TRANSACTION` and include the
    original transaction in `details.existing_transaction`. Returning the existing record lets clients
    reconcile without a second request. (An alternative reading – returning `200` with the existing
    transaction, "idempotent replay" – was considered; `409` was chosen because the brief asks for a
    response that *indicates the transaction already exists*, and because the duplicate request may carry
    a different amount/type, which must not be mistaken for a success.)
17. **Only successful transactions consume a `reference_id`.** A debit rejected for insufficient balance
    is not recorded, so the same `reference_id` can be retried later. Rejected or failed attempts are not
    persisted anywhere (no "failed" status) because the brief defines a transaction as something that
    changed the balance.
18. **Immutability** is enforced twice: the API has no `PUT`/`PATCH`/`DELETE` routes for transactions
    (they answer `405`), and database triggers abort any `UPDATE`/`DELETE` on the `transactions` table.
19. **Balance is stored on the account** (not recomputed from history on every read) and is updated in the
    same database transaction as the inserted transaction row. Row locks (`SELECT … FOR UPDATE` on
    PostgreSQL) / `BEGIN IMMEDIATE` (SQLite) serialise concurrent writers, and the `CHECK (balance >= 0)`
    constraint guarantees the no-overdraft rule even if the application were bypassed. A helper that
    recomputes the balance from the transaction log exists (`compute_balance_from_history`) and is used by
    the tests to assert consistency.
20. **A debit equal to the full balance is allowed** (balance becomes `0.00`); only debits *greater* than the
    balance are rejected.
21. **Two creation routes exist for convenience:** `POST /accounts/{account_id}/transactions` (RESTful,
    recommended) and `POST /transactions` with `account_id` in the body (the brief lists `account_id` as a
    transaction field). Both share the same logic and validation.

## Transaction history

22. **Latest-first ordering** uses `created_at DESC` with the internal insertion sequence as tie-breaker so
    results are deterministic even when two transactions share a timestamp.
23. **Pagination is 1-based**: `page` ≥ 1 (default 1), `limit` 1–100 (default 20). The response contains
    `page`, `limit`, `total_records`, `total_pages`, `has_next`, `has_previous`.
24. **A page beyond the last page returns an empty list** with the usual metadata rather than an error; a
    `page`/`limit` outside the allowed range is a `400 VALIDATION_ERROR`.
25. **`total_records` / `total_pages` honour the `type` filter.**

## Error handling and status codes

26. **One error envelope everywhere:** `{"error": {"code", "message", "details"}}`.
27. **Status codes:** `400` for malformed / schema-invalid requests (including malformed JSON and invalid
    pagination), `404` for unknown resources, `405` for mutations of immutable resources,
    `409` for duplicate `reference_id`, `422` for well-formed requests rejected by a business rule
    (insufficient balance, same-account transfer), `500` for unexpected failures (with nothing persisted).
    FastAPI's default of `422` for schema validation errors was deliberately changed to `400` so that `422`
    unambiguously means "business rule violation".

## Transfers (bonus)

28. **A transfer produces two transactions** – a `debit` on the source and a `credit` on the destination –
    plus a `transfers` record; all three are written atomically. The legs carry `transfer_id` so they can be
    traced back.
29. **`reference_id` on a transfer is optional.** When supplied it is applied to both legs and must be
    unused on *both* accounts (otherwise `409 DUPLICATE_TRANSACTION`, nothing persisted). When omitted the
    server generates `TRF-<uuid>`.
30. **`description` is optional.** When omitted the legs get `Transfer to account <id>` /
    `Transfer from account <id>`.
31. **Transfers to the same account are rejected** (`422 SAME_ACCOUNT_TRANSFER`) – also enforced by a
    database check constraint.
32. **Accounts are locked in a deterministic order** (sorted by id) so two concurrent transfers in opposite
    directions cannot deadlock.

## Operational

33. **Concurrency model:** the API is safe for concurrent requests against a single database. With SQLite,
    writers are serialised by the database (one writer at a time, 30 s busy timeout), which is appropriate
    for local use and tests; PostgreSQL is the intended choice for real multi-user load.
34. **No soft deletes / account closure, no reversal transactions.** A correction would be modelled as a
    new compensating transaction, never as an edit.
